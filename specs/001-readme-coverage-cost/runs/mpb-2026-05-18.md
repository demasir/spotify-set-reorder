## Subjective notes

The sleep-prep arc landed. Trimming 50 → 10 tracks for ~45 min worked
better than sequencing the full playlist would have; the contemplative
center (Lenine acoustic + Mariana Aydar) held the room steady, and
the explicit "O Último Pôr do Sol" → "Resposta" close paid off the
"preparar pra dormir" intent narratively. The biggest sequencing
tension was the early BPM jump (94 → 100 → 95 → 103) which arguably
broke a strict descending rule — declared as a deliberate "expansion
before descent" in the preview and worked in practice. User verdict
on listening: ficaram ótimas.

## Surprises

- MPB BPM/key coverage on public databases was patchier than electronic
  catalogs (verified 50%, partial 42%, only 6% unknown — better than
  feared, but the `partial` share is high). Many tracks returned a key
  without a BPM, or vice versa, where Tunebat/SongBPM had thin data.
- Half-time / double-time ambiguity hit harder than expected — Carnavália
  returned 167 BPM (clearly double-time of ~83), Quase Um Segundo
  returned 177 BPM (double-time of ~88). The skill handled them as
  `partial` with felt-tempo annotation, which was the right call but
  would benefit from explicit guidance in Step 2.
- Mid-run, the maintainer flagged that enriching all 50 tracks when the
  intent obviously only needed the slowest ~10 was wasted work. That
  feedback was captured in memory (`feedback-partial-enrichment-ok`)
  and queued as a skill update (task #13 in the working session,
  follow-up commit deferred to a future PR — not part of this feature).

## How tokens were counted

This run executed inside a multi-run session that also included T005,
a retrospective T007, install-verify work for the spec-kit feature,
and README planning. The session's `/usage` total ($14.81, ~1.06M
non-cache tokens, 80 web searches) is therefore CONTAMINATED — it
mixes per-run skill cost with overhead unrelated to any single
reorder. A first attempt to attribute via proportional web-search
split was rejected as misleading.

The `tokens_observed` figure above (`600000`) is instead a
**projection from a clean-baseline measurement** taken in a separate
fresh Claude Code session that ran the skill against a 4-track
playlist with no other workload — see `singer-songwriter-2026-05-18.md`
for the raw `/usage` data ($1.03, 62k non-cache tokens, 4 web
searches). Methodology: haiku web-search cost scales near-linearly
with track count (4 → 50 searches = ~12.5×); opus cost scales
sub-linearly due to cache benefits at session length (~5–7×).
Net projection: ~600k non-cache tokens for a 50-track full-enrichment
run. This is an estimate, not a measurement. Per-run direct
measurement is deferred work tracked at issue #4.
